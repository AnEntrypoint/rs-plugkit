rs-plugkit prose::resolve source-repo tier: read_from_cache_root reads <cache>/gm.config.json once and picks the directory per key namespace. A gates/* key takes messages.gates_dir, a residual/* key takes messages.residual_dir, and the remainder AFTER the namespace prefix becomes the file stem, so gates/long-gap-no-instruction reads <cache>/<gates_dir>/long-gap-no-instruction.md. Any other key, or a namespace whose field is absent or non-string, falls back to instructions.dir (default prose) with the FULL key as the stem, which is the pre-messages behaviour every older config repo relies on. Tier order is unchanged: project-local .gm/instructions/<key>.md, then this cache tier, then the compiled default. fsm.graph is NOT part of this: it resolves relative to the cache root in fsm.rs::source_repo_graph_path and never enters prose.rs. Separately, the legacy .gm/instructions/source.json tier short-circuits read_from_source_repo and never consults gm.config.json for ANY key, prose included.

Verifying prose resolution natively: pkfs::read_to_string/write/exists are unconditional no-ops on non-wasm32 targets, so linking rs-plugkit as an rlib and calling resolve_detailed always returns the compiled default and proves nothing. The working method is an out-of-repo binary crate that pulls the REAL sources in with #[path = "/abs/path/crates/plugkit-core/src/prose.rs"] mod prose; plus the same for config_path.rs, and declares sibling modules named pkfs (real std::fs), config (SOURCE_CACHE_REL plus user_cache_root) and orchestrator::state::now_ms so every crate:: reference in prose.rs resolves. The wasm-only report() is cfg'd out automatically. Run the binary with its cwd set to a fixture holding .gm/config-source-cache and HOME pointed at an empty dir to keep the user-wide tier out of the way. Also note the whole crate does NOT compile for the host target (config.rs calls the wasm32-gated resolve_and_report unconditionally, 19 errors at baseline); the real compile gate is cargo check --target wasm32-wasip1 --features slim.
